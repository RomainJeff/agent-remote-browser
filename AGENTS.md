# AGENTS.md

- Use a feature branch only for one large feature whose slices depend on each other and only make sense together; changes that are unrelated or can each ship on their own go straight to `main` as separate PRs, however many there are. Such a feature goes through a feature branch: create `feature/<name>` from `main`, open its PR to `main` as a draft once it has its first commit, then branch each slice from the feature branch and open it as a small PR targeting that branch. Keep the feature PR description current: under a `## Sub-PRs` heading, list every slice PR as a task item (`- [x]` merged, `- [ ]` open or planned) with its link and a one-line summary, and update it whenever a slice PR is opened, merged, or dropped. Merge slices into the feature branch once their own CI and review are done, keep the feature branch up to date by merging `main` into it (never rebase or force-push it), and once every slice is in and the full feature works, mark the feature PR ready for review (drafts get no bot review) and merge it after that review. The `CHANGELOG.md` entry lands once, in the last slice, dated for the day the feature PR merges.
- Right after creating a pull request, run the `merge-risk` skill on it and post its output as a PR comment. After creating a pull request, stay with it until CI and automated review bots have finished; passing checks alone do not mean the review is complete. Wait for the checks on the current head commit to be terminal with a single backgrounded call (e.g. `gh pr checks --watch`). Do not poll in the foreground on a timer, which mostly buys repeated snapshots of an unchanged PR and dies at the tool timeout. Triage review feedback by concrete impact before changing code. Fix only issues that materially affect correctness, security, reliability, a core user flow, or an explicit requirement of the change. A suggestion being actionable is not enough: do not expand scope for style preferences, speculative risks, optional refactors, or minor improvements. Briefly dismiss or defer those suggestions with a reason; important issues unrelated to the change should be reported separately unless they block safe delivery. Push necessary fixes and repeat only while material issues remain or new checks or reviews are pending. Do not merge while review bots are still pending or material issues remain unresolved; dismissed or deferred suggestions do not block completion.
- Treat auth, secret handling, sandbox boundaries, host commands, and integrations as security-sensitive. Keep tests deterministic and offline by default.
- Before adding complexity for a speculative or vanishingly unlikely race or security edge case, explain the concrete failure mode, likelihood, and complexity cost to the user and get their buy-in. Do not silently expand scope for theoretical robustness.
- Every new implementation plan, architecture proposal or multi-ticket breakdown, including automatically generated plans, gets an independent `founding-engineer` review before presentation or execution. Follow the plan-review protocol in `.agents/skills/principle-laziness-protocol/SKILL.md`. Progress checklists are not new plans. The reviewer reports advice without editing the plan; the plan owner exposes the findings and records their disposition. This adds no human approval gate.
- This is a public repository: assume all tracked content and diffs are public. Never commit secrets, `.env` files, private URLs, personal/customer data, or real production data; use fake placeholders. Review `git status` and the staged diff before committing, and never force-add ignored files. If private data appears, stop and alert the maintainer.
- Treat every visible word as UI. Start UX work by asking what can be removed, and prefer progressive disclosure over persistent explanation or status chrome. If a PR adds user-facing copy, its description must quote the copy, explain why it is necessary, and say why removing it or revealing it only when relevant would not work.
- Keep code simple: reuse existing primitives and one source of truth, remove duplication and unused flexibility, and avoid speculative abstractions. Add an interface when it protects a real external or platform boundary, not for its own sake.
- Parallel delegated tasks coordinate through their launching orchestrator using `.agents/references/coordination.md`. Workers report cross-task discoveries before changing shared assumptions or scope; the parent relays decisions and obtains acknowledgement from affected active workers. Verify results against the current brief before integration.
- PR descriptions say why the change exists, what changed, and how it was tested. Write Why as the product reason (what was wrong and what this changes); never a third-person briefing of a named person; the maintainer is the author.
- Commit messages, PR descriptions, issues, and review replies are public too. Describe test results in words instead of pasting tool output, and never include anything that identifies a person, machine, or account: local paths, usernames, hostnames, signing identities, legal entity names, Apple Team IDs, API key IDs, issuer or tenant IDs, account emails, or the accounts, machines, and files that secret values came from. Naming the secrets a workflow reads is fine; use placeholders when a value must be shown.
